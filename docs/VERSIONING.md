# Versioning policy

Adapted from HallPass docs/VERSIONING.md (Apache-2.0, same author).

Porch has several public interfaces. The binary version tells you which release you are running. Each interface below
has its own compatibility rules. A release lists every interface change in [`CHANGELOG.md`](../CHANGELOG.md).

| Interface | Version marker | Where it is defined |
|---|---|---|
| Binary / release | `vMAJOR.MINOR.PATCH[-PRERELEASE]` (SemVer 2.0.0) | git tag, `porch version` |
| Management API | URL prefix `/api/v1` | OpenAPI 3.1 document [`api/openapi.json`](../api/openapi.json) (generated by `porch openapi`) |
| OIDC / OAuth endpoints | the standards they implement | `/.well-known/openid-configuration`, [API.md](API.md) |
| Forward-auth contract | `/outpost/*`, `/.porch/*`, `X-Porch-*` response headers | [API.md](API.md), `site/operators/forward-auth.md` |
| Events | type `porch.<area>.<entity>_<action>.v1`, subject `evt.porch.…` | `internal/outbox` |
| Database schema | goose migration number (`0001`, `0002`, …) | `internal/store/migrations/` |
| Backup format | manifest `version` (currently 1), schema version recorded in the manifest | `internal/backup`, ADR-0042 |
| Configuration | YAML keys and `PORCH_*` variables | `internal/config`, `deploy/porch.container.yaml` |

## Binary and releases

[Semantic Versioning 2.0.0](https://semver.org/spec/v2.0.0.html), tags `vX.Y.Z`; pre-releases `vX.Y.Z-rc.N` (or another
`-PRERELEASE` suffix). The release workflow rejects any other tag format, and every tag needs a
`## [X.Y.Z] - YYYY-MM-DD` section in the changelog.

The version is embedded at link time (`internal/buildinfo`: `Version`, `Commit`, `Date`) and printed by
`porch version` (`--json` for machines). Archives are named `porch_X.Y.Z_<os>_<arch>.tar.gz`. Container image tags
drop the `v`: `ghcr.io/aurimasniekis/go-porch:X.Y.Z`, mirrored to `docker.io/aurimasniekis/porch:X.Y.Z` when Docker Hub
publishing is configured. `latest` only follows final releases, never pre-releases. The release procedure is in
[RELEASING.md](RELEASING.md).

The binary version summarizes the interfaces below:

- **MAJOR**: a breaking change to any public interface: a new management API major version (`/api/v2`) or removal of
  `/api/v1`, removal of an event type version, removal or renaming of a configuration key or `PORCH_*` variable, a
  backup format that older restores cannot read, or an upgrade that needs a manual step.
- **MINOR**: new features, additive API and event changes, new configuration keys, new database migrations,
  deprecations.
- **PATCH**: bug and security fixes with no interface change. A patch release contains a database migration only when
  a fix needs one, and the changelog says so.

Before 1.0.0, MINOR releases may contain breaking changes. Each one is listed under **Changed** or **Removed** with
upgrade instructions.

Security fixes are released as PATCH releases for the latest MINOR line. Older lines are not maintained unless a
release note says otherwise.

## Management API (`/api/v1`)

- The committed [`api/openapi.json`](../api/openapi.json) is the contract. CI fails when it differs from what the code
  generates (`make api-check`), so every API change shows up in the diff of that file and of the generated web types.
- Changes within `/api/v1` are additive only: new endpoints, new optional request fields, new response fields, new
  values in fields documented as open sets, new problem `code` values. Clients must ignore unknown response fields.
- Breaking changes (removing or renaming fields or endpoints, changing types or semantics, new required inputs,
  stricter validation of existing inputs) require `/api/v2`. `/api/v1` and `/api/v2` are then served side by side for at
  least one MINOR release, and the changelog announces the deprecation first.
- Deprecations are marked in the OpenAPI document (`deprecated: true`) and listed under **Deprecated** in the changelog
  at least one MINOR release before removal.
- Problem `code` strings (RFC 9457 responses) are never reused for a different meaning.
- Automation tokens (`porch_at_…`), `Idempotency-Key` and ETag/If-Match semantics are part of the API contract.

## OIDC, OAuth and forward-auth

- OIDC and OAuth endpoints follow their specifications. Changing an advertised capability in discovery (for example
  removing a signing algorithm, grant type or response type) is a breaking change, unless it is a security fix, in
  which case it is listed under **Security** with the reason.
- Claims issued in ID tokens and access tokens are additive within a MAJOR version. Removing or renaming a claim is a
  breaking change.
- Forward-auth paths and `X-Porch-*` identity headers follow the same rules as the API.

## Events

- Event types carry a version suffix (`.v1`). Payload changes within a version are additive; consumers must ignore
  unknown fields. Incompatible payload changes use a new type version (`.v2`), and the old version is published
  alongside it for at least one MINOR release.

## Database schema (migrations)

- Migrations are embedded, numbered sequentially, applied in order at startup or with `porch migrate`, and
  **forward-only**. Applied migrations are never edited; fixes ship as new migrations.
- A pre-migration snapshot is written before any migration runs on an existing database.
- A binary refuses a database whose schema is newer than it supports ("database schema is newer than this binary").
  The only way back is restoring a backup or pre-migration snapshot taken before the upgrade.
- Each release's changelog states whether it contains migrations, and whether they are long-running (data rewrites).
- Upgrades are supported from the previous MINOR release.

## Backups

- The manifest `version` fixes the backup layout and signature scheme. A new layout uses a new version, and restores
  keep reading every version that can still exist within a supported retention.
- A backup records its schema version. Restoring it with a newer binary migrates it forward on first start; an older
  binary refuses a database from a newer schema.

## Configuration

- Configuration keys and `PORCH_*` variables are part of the public interface. Unknown keys and unknown `PORCH_*`
  variables are errors, so removing or renaming a key is a breaking change. Keys are deprecated first: still accepted,
  with a warning, for at least one MINOR release.
- A changed default that weakens a security property is called out, with the reason, in a **Security** changelog entry
  and needs an ADR labelled **security-relevant change** ([DECISIONS.md](DECISIONS.md)).

## Changelog

[`CHANGELOG.md`](../CHANGELOG.md) follows [Keep a Changelog 1.1.0](https://keepachangelog.com/en/1.1.0/), with sections
Added, Changed, Deprecated, Removed, Fixed, Security. Entries name the affected interfaces (API, events, schema,
migration, backup format, config). An entry never claims more than the evidence supports: *implemented* (the code
exists), *tested* (automated tests pass) or *verified externally* (checked against a real external system or reviewed
outside the project), matching [IMPLEMENTATION_MATRIX.md](IMPLEMENTATION_MATRIX.md).
