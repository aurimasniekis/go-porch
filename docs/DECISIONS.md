# Architecture decision records

Format: context → decision → consequences. ADRs marked **security-relevant change** relax or deviate from a stated
security requirement and need operator review. ADR numbers are stable and never reused.

## ADR-0001 — Modular monolith on Go + SQLite

**Context.** Target deployments are a single small host (homelab, VPS) serving tens to hundreds of users.
**Decision.** One static binary, `modernc.org/sqlite` (pure Go, `CGO_ENABLED=0`), modules as `internal/` packages with
one-directional dependencies (edges → domain → platform).
**Consequences.** Simple operations and backups; vertical scaling only; single writer (see ADR-0002). No HA in v1.

## ADR-0002 — Store: single writer, reader pool, forward-only migrations, sqlc

**Decision.** Adapted from HallPass: 1-connection writer with `BEGIN IMMEDIATE` and jittered busy retry, read-only reader
pool, WAL, `synchronous=FULL`, goose embedded migrations (forward-only; `Down` is a no-op), pre-migration `VACUUM INTO`
snapshot, `flock` on the data directory, refusal of network filesystems, typed queries generated by sqlc (drift-checked in
CI). Dynamic list/filter queries use hand-written SQL with bound parameters only.
**Consequences.** Downgrades refused (`ErrSchemaTooNew`); rollback = restore the pre-migration snapshot.

## ADR-0003 — Keyring: KEK + versioned purpose keys

**Decision.** A 32-byte KEK file (0400, outside the DB, required in production, auto-generated only in development)
wraps per-purpose AES-256-GCM keys: `field` (sealed columns), `token` (HMAC lookups of bearer tokens and codes),
`signing` (wraps OIDC signing private keys), `backup-meta`. Sealed values bind AAD `table|column|row-id`. A canary verifies
the KEK at startup. One registry (`keyring.Columns`) lists every sealed column; reseal, retire guards and backup checks use
it (fixes HallPass SR-36/37).
**Consequences.** DB theft alone does not reveal secrets. KEK loss = data loss unless escrowed in backups (ADR-0018).

## ADR-0004 — Logical tenant isolation, DB-enforced

**Decision.** Every tenant-scoped table has `tenant_id`, a `UNIQUE (tenant_id, id)` key and composite FKs for references
(e.g. `role_assignments(tenant_id, role_id) → roles(tenant_id, id)`), so a row cannot reference another tenant's row.
Repository functions take a `tenancy.Scope` constructed only by `tenancy.Resolve` after checking membership or an
explicit share. Installation operators are separate (`installation_role_assignments`); tenant roles never imply
installation capabilities. Cross-tenant app use requires an `app_shares` row.
**Consequences.** Same process/DB/KEK: not a boundary against host compromise or Porch bugs (documented).

## ADR-0005 — External identities keyed by issuer + subject; no email auto-linking

**Decision.** `external_identities (provider_id, issuer, subject)` is unique; email is an attribute. A new upstream
identity whose email matches an existing user is **not** linked automatically. Linking requires a logged-in user,
step-up, and a fresh upstream authentication of the second identity (for Google: a completed interactive sign-in,
ADR-0047); it is audited. A new identity whose email already belongs to a user (primary or additional address) is
not enrolled through a domain rule or invite either: the login is refused with `email_in_use` and the person is told
to sign in another way and link the account (0.1.1; before, a second user was created).
**Consequences.** Users who switch Google accounts need an explicit link or admin action. An installation's first
owner, created at setup with their own email, links Google from their account page before signing in with it.

## ADR-0006 — Domain enrollment by validated evidence, with provenance

**Decision.** `domain_rules` map a domain (unique per installation) to a tenant + provider with evidence
`workspace_hd` (validated `hd` claim of a verified Google ID token — never the email suffix, never the `hd=` request hint)
or `verified_email` (opt-in, `email_verified=true`, labelled weaker in UI). Mode `invite_only` or `jit`. Memberships and
assignments carry `source` (`manual`, `domain_rule:<id>`, `dirsync:<id>`, `terraform`). Re-evaluation runs at every login
and periodically; lost evidence removes derived grants only. Domain rules never grant admin roles unless explicitly
selected (UI warning).

## ADR-0007 — Google federation via go-oidc; hourly silent recheck

**Decision.** `coreos/go-oidc/v3` verifier (issuer, audience, RS256 allowlist, expiry, nonce). State, nonce and PKCE
verifier are stored server-side (sealed) and bound to a short-lived `__Host-porch_oidc` cookie. Federated sessions are
re-checked with `prompt=none` at most hourly (on the next interactive request after the deadline); failure ends the
session. Optional Directory API sync (fake-tested only; real Google **not verified**).

## ADR-0008 — Backup login: two-step password + titled recovery answers, shared reserve-before-hash lockout

**Context.** Google is the primary login; the backup login must work when Google is unavailable or the account is lost,
without becoming the weakest door.
**Decision.**
- **Credential.** A password plus at least 3 user-defined **recovery pairs**: a custom title (a hint the user writes,
  like a security question, e.g. "Street I grew up on") and a short free-text answer. See ADR-0009.
- **Verifiers.** Two Argon2id (m=64 MiB, t=3, p=2, calibrated) PHC verifiers: one over the NFKC password, one over the
  length-prefixed sequence of canonical answers (all answers in one hash, so no per-answer oracle). Both PHC strings and
  the titles are sealed with the `field` key (AAD bound to user + column), which acts as a pepper against DB-only theft.
- **Two-step flow.** Step 1: handle + password. Only if the password is correct does Porch issue a single-use challenge
  (5 min TTL, bound to a `__Host-` cookie and the source) and show the user's titles. Step 2: answers. A session is
  created only after both steps.
- **Lockout (shared budget).** State `backup_lockouts(user_id, failures, locked_until, level)`. **Each step reserves an
  attempt atomically** (`BEGIN IMMEDIATE`: refuse if locked or `failures ≥ threshold`, else `failures += 1`) **before**
  hashing. A failed step locks when `failures` reaches the threshold (`locked_until = now + duration·2^level`, cap,
  `level++`). A correct password only releases its own reservation; it never resets the counter or the level, so knowing
  the password buys no extra answer guesses. Full success resets `failures` (and decays `level`). Policy: threshold 1,
  duration 6 h, escalation ×2 capped at 48 h (configurable). N parallel attempts cannot exceed the threshold.
- **Other layers.** Per-source throttle (IPv4 / IPv6 /64) checked before the account counter; installation-wide circuit.
  Unknown handle and locked account take the same path as a wrong password (dummy hash, generic response, same timing).
- **Scope.** Lockout affects only the backup mechanism; Google login and existing sessions keep working.
- **DoS mitigations.** Optional separate login handle (not the email); owner unlock via authenticated session +
  step-up; `porch admin unlock-backup` on the host. A global "lock everyone" switch exists only as an explicit config flag
  with a startup warning. No remote "lock user" API.
- **Offline recovery.** `porch admin recover` (needs data-dir lock + KEK) issues a one-time 15-minute login link,
  audited, with a persistent alert until acknowledged. No universal recovery password.

## ADR-0009 — Recovery answers: user-chosen, titled, shown after the password, reusable until rotated — **security-relevant change**

**Context.** The original brief preferred one-time recovery codes generated by Porch. The operator decided (2026-10-24)
that recovery material is created by the person and carries custom titles, like security questions.
**Decision.**
1. **User-chosen titles and answers.** Minimum 3 pairs, maximum configurable (3–12). Titles: 1–120 characters,
   distinct. Answers: free-text phrases canonicalised as NFKC → lowercase → punctuation removed → whitespace collapsed.
   The enrollment UI offers an optional **"suggest random words"** action (EFF large wordlist, `crypto/rand`) for any
   answer. Enrollment requires re-typing every answer.
2. **Titles shown only after a correct password** (step 2 of ADR-0008). This creates a **password oracle**: an attacker
   learns whether a guessed password is right. Accepted trade-off for usability; mitigated by the shared lockout budget
   (a password guess costs the same as a full attempt) and documented.
3. **Reusable until rotated.** Answers are not consumed on use. Rotation requires step-up.
4. **Strength gate.** Enrollment rejects: answers that repeat, that contain the password or the title text, answers or
   passwords on the common lists, and combinations whose estimated strength (password + answers) is below the configured
   minimum. The user's name, email and handle count against strength.

**Consequences.** Human-chosen answers, especially to self-written "security questions", have much lower and less
predictable entropy than random picks, and titles can hint at publicly discoverable facts; Porch documents their strength
as an *estimate*, not a guarantee, and the UI warns against answers findable online. The table below applies only when
the user accepts random suggestions (EFF large list, 7776 words, 12.92 bits/word); it shows time to search half the
answer space **in addition to** the password. Offline attack requires the DB **and** the KEK (sealed verifiers); online
attack is bounded by the lockout (1 failure → 6 h, doubling to 48 h).

| Random words | Bits | 10 guesses/s | 10³ guesses/s | 10⁵ guesses/s |
|---|---|---|---|---|
| 3 | 38.8 | 745 years | 7.45 years | 27.2 days |
| 4 | 51.7 | 5.8×10⁶ years | 5.8×10⁴ years | 579 years |
| 5 | 64.6 | 4.5×10¹⁰ years | 4.5×10⁸ years | 4.5×10⁶ years |
| 6 | 77.5 | 3.5×10¹⁴ years | 3.5×10¹² years | 3.5×10¹⁰ years |
| 8 | 103.4 | 2.1×10²² years | 2.1×10²⁰ years | 2.1×10¹⁸ years |
| 12 | 155.1 | 7.7×10³⁷ years | 7.7×10³⁵ years | 7.7×10³³ years |

10³–10⁵ guesses/s is a rough range for a well-resourced attacker against Argon2id at 64 MiB; the online lockout allows
fewer than 10 guesses **per day**. Residual risks: answers written down or socially discoverable stay valid until rotated;
the password oracle lets an attacker confirm a phished/reused password at the cost of one lockout slot; restoring an old
backup restores old answers (mitigated by `restore --invalidate-backup-credentials`).

## ADR-0010 — Step-up window 5 minutes

**Decision.** Sensitive operations require `auth_time` within 5 minutes: recovery enrollment/rotation, secret rotation,
key operations, provider/domain changes, installation-role changes, backup configuration, policy writes, identity linking.
Satisfied by a fresh upstream re-auth (`prompt=login`, `max_age=0`, verified `auth_time`; for Google, which cannot
re-authenticate on request, a completed interactive sign-in, ADR-0047) or the local backup credential.

## ADR-0011 — Authorization: RBAC + conditional grants + deny policies, default deny

**Decision.** Permissions `<resource_type>:<action>`. Roles bundle permissions; role bundles compose roles; groups nest.
Both graphs are DAGs with cycle detection and depth ≤ 5 on write, re-validated by the evaluator. Assignments bind a
subject (user | group | service account) to a role at a scope (tenant | resource type | resource) with optional condition
policy, expiry and source. Evaluation order: authenticated → tenant gate → collect grants → deny policies (any match or
evaluation error ⇒ deny) → allow if some grant's condition passes → default deny. Context attributes are server-derived;
client-supplied context is accepted only by the simulator and flagged. Every decision has an explain trace. Decision
cache keyed `(tenant, principal, authz_epoch)`; the epoch is bumped in the same transaction as any authz change.

## ADR-0012 — Adopt expr-lang/expr for conditions

**Decision.** Versioned typed environment (`v1`: `principal`, `resource`, `action`, `context`, `now`) with `expr.Env`,
`expr.AsBool`, all builtins disabled except an approved pure set, custom pure helpers (`inGroup`, `hasAttr`, `before`,
`cidrMatch` on server-provided values), node limit, VM memory budget, source and input size limits. Compiled on write
(stored hash), fail closed, fuzz-tested.

## ADR-0013 — OIDC provider via zitadel/oidc v3

**Decision.** `github.com/zitadel/oidc/v3/pkg/op` with a Porch SQLite `op.Storage`. Authorization code + PKCE only (S256
required for all clients by default), no implicit, no ROPC. Exact redirect URI match (RFC 8252 loopback port exception).
Discovery, JWKS, UserInfo, revocation, introspection (confidential clients/resource servers), RP-initiated logout (ends
the Porch session and revokes that client's refresh tokens), client credentials for service accounts.
**Consequences.** No front-/back-channel logout in v1 (documented).

## ADR-0014 — Token formats

**Decision.** Access tokens: RFC 9068 JWT, ~10 min, `aud` from the client's registered API audiences or RFC 8707
`resource`. Refresh tokens: opaque, stored as HMAC, rotating, family id, reuse ⇒ revoke family. Signing: ES256 default,
RS256 allowed per client; keys sealed in the keyring, rotated with overlap. `sub` = stable installation-wide user public
ID. Namespaced claim `porch = {v:1, tenant:{id,slug}, roles:[…audience-specific], groups?, entitlements?}` gated by
per-client disclosure; size cap (omit and set `porch.truncated`).

## ADR-0015 — Forward-auth with per-app-host callback

**Decision.** `/outpost/auth` for Caddy `forward_auth`, Traefik ForwardAuth and nginx `auth_request`. Each protected
host proxies `/.porch/callback` to Porch, which sets a **host-only** `__Host-` cookie — no parent-domain cookie.
Redirect targets must be registered hosts. Identity headers are configurable; proxies must strip inbound `X-Porch-*`
and `Remote-*` (docs + tests).

## ADR-0016 — Management API: code-first Huma v2, OpenAPI 3.1

**Decision.** `/api/v1` with Huma v2; `porch openapi` emits `api/openapi.json`, committed and drift-checked; TS types via
`openapi-typescript` + `openapi-fetch`. Cursor pagination, filters, RFC 9457 errors, `ETag`/`If-Match` on row version,
`Idempotency-Key` on creates (secret-bearing responses never cached). Every resource has `managed_by` and
`last_changed_by` (provenance, not a security boundary).

## ADR-0017 — Automation tokens

**Decision.** `porch_at_<id>_<secret>`; stored as HMAC under the `token` key; tenant-scoped with explicit permissions;
expiry required (max configurable, default 365 days).

## ADR-0018 — Backups encrypted to an offline age recipient, with KEK escrow

**Decision.** `VACUUM INTO` → manifest → s2 → age (X25519 recipient; Porch holds no identity) → S3 via minio-go. The
KEK is escrowed encrypted to the same recipient (toggleable, default on). Restore into a clean instance bumps the
security epoch, rotates signing keys and audits the restore.
**Consequences.** Whoever holds the offline identity can restore everything; it must be stored offline.

## ADR-0019 — Audit chain, outbox, pulse

**Decision.** Hash-chained `audit_events` appended in the mutation's transaction (failure aborts the mutation); JSONL
sink (ECS-aligned) for log shipping. Outbox rows in the same transaction; a relay publishes to pulse NATS
(`evt.porch.<area>.<entity>.<action>`, type `porch.<area>.<event>.v1`, `WithID(ulid)`), with backoff + jitter (cap 5 min)
and dead-letter after 24 h or 50 attempts. Pulse outages never block logins.

## ADR-0020 — Edge trust

**Decision.** Explicit `public_url`/issuer. Trusted proxies by CIDR with right-to-left `X-Forwarded-For` walk.
Cloudflare mode trusts `CF-Connecting-IP` only from configured Cloudflare ranges (and optionally requires Authenticated
Origin Pulls client certs); `Cf-Access-*` headers are never trusted.

## ADR-0021 — Sessions

**Decision.** Server-side sessions (`__Host-porch_session`, HMAC-hashed token), idle 8 h / absolute 12 h (per-tenant
override), rotation on login/step-up/privilege change, `security_epoch` (installation) and per-user epoch invalidate all
sessions at once.

## ADR-0022 — Identifiers and time

**Decision.** IDs `<prefix>_<26 base32>` (UUIDv7, HallPass ADR-0010); UTC Unix microseconds in the DB.

## ADR-0023 — UI stack and CSP

**Decision.** React 19 + Mantine 8 + TanStack Router/Query/Store, Vite, embedded with `go:embed`. CSP:
`script-src 'self' 'nonce-…'`, `style-src-elem 'self' 'nonce-…'`, `style-src-attr 'unsafe-inline'` (Mantine style
attributes), per-request nonce injected into `index.html`.

## ADR-0024 — Private management listener

**Decision.** `/metrics`, `/healthz`, `/readyz`, pprof (off by default) only on `127.0.0.1:9464`. The public listener
defaults to `127.0.0.1:8080`.

## ADR-0025 — Setup tokens are issued on the host while Porch is stopped

**Context.** The first owner must not be creatable remotely without host access, and no default credentials may exist.
**Decision.** `porch admin setup-token` opens the data directory (taking its `flock`) and the KEK, so it runs before the
first `porch serve` or while the server is stopped. Tokens are single-use, expire (default 1 h), are stored as HMACs, and
can only be consumed while no installation operator exists, inside one `BEGIN IMMEDIATE` transaction. Consuming creates a
setup session capped at 1 h whose purpose is to enroll a real login method.
**Consequences.** One short stop of the service on first install (or `docker compose run porch admin setup-token` before
`up`). No setup URL is ever printed to server logs.

## ADR-0026 — Until M5, tenants are managed by installation operators only (superseded by ADR-0038)

**Context.** Tenant-level admin roles need the authorization engine (M5).
**Decision.** In M1–M4 the management API resolves tenant scopes only for installation owners/admins
(`tenancy.ResolveForOperator`, recorded as `via: operator` in audit details). Tenant members get a `ViaMembership` scope
for their own data (portal, OIDC) but no management rights.
**Consequences.** Temporary; replaced by `authz` checks (`tenant:manage`, `member:manage`, …) in M5 without API changes.

## ADR-0027 — How the hourly upstream recheck is enforced

**Decision.** A federated session whose last upstream confirmation is older than `session.upstream_recheck` (1 h) cannot
use the management API (`401 upstream_recheck_required` with an `action` URL) and page navigations are redirected through
`/login/{provider}?intent=recheck` (`prompt=none`, `login_hint`). Success updates `upstream_checked_at` and re-evaluates
rule-derived memberships with the fresh token; `login_required`, a different account, an invalid token or a disallowed
`hd` revoke the session. `/me` and `/logout` are exempt so the UI can render. Evidence re-evaluation therefore happens
at every login and every recheck; deleting a domain rule removes its derived memberships in the same transaction. A
separate periodic job is unnecessary because nothing can change the evidence without a fresh token.
**Consequences.** An idle browser tab keeps an unconfirmed session until its next request; it cannot act with it.

## ADR-0028 — Recovery-answer strength is estimated per answer

**Context.** zxcvbn scores space-joined common words ("red dog cat") as brute force (~10^10.8 guesses).
**Decision.** Each canonical answer is estimated separately (titles, name, email and handle as known context) and the
log10 guesses are summed; enrollment requires ≥ 10^8 for the answers alone and ≥ 10^14 for password + answers, plus a
zxcvbn password score ≥ 3 and length ≥ 12.
**Consequences.** Still an estimate (documented as such in the UI and ADR-0009); random-word suggestions comfortably pass.

## ADR-0029 — Invites and `verified_email` evidence

**Decision.** An invite is consumed only by an upstream login whose `email_verified` is true and whose email matches.
Under an `invite_only` domain rule, the resulting membership carries the rule's source (so losing the domain evidence
removes it); a plain invite yields source `invite:<id>` (manual-like, never removed automatically). `verified_email`
rules accept the email domain of a verified email from the rule's provider only and are labelled weaker than
`workspace_hd` in the API and UI.

## ADR-0030 — Implement zitadel's `op.Server`, not its legacy `Storage`

**Context.** zitadel/oidc's legacy `Storage` path builds ID and access tokens from one `GetAudience()` value (so API
audiences would leak into ID tokens or clients into access tokens), signs access tokens without RFC 9068's `typ: at+jwt`,
and leaves refresh-token semantics implicit.
**Decision.** Porch implements `op.Server` (embedding `UnimplementedServer`). zitadel keeps the HTTP layer: request
decoding, redirect-URI matching (exact; RFC 8252 loopback port exception for native clients), client-authentication
parsing and error rendering. Porch issues every token itself: ID tokens (`aud` = client, `azp`, `nonce`, `at_hash`),
RFC 9068 access tokens (`aud` = registered API audience / RFC 8707 `resource`, else the client), opaque rotating refresh
tokens with family reuse detection, and implements discovery (incl. RFC 9207 `iss`), JWKS, userinfo, introspection,
revocation and RP-initiated logout. Unsupported: implicit/hybrid flows, request objects, dynamic registration, device
flow, token exchange (they return the library's "unsupported" errors).

## ADR-0031 — Re-authentication for `prompt=login` and `max_age`

**Decision.** `max_age` is satisfied by any authentication after the authorization request (OIDC Core §3.1.2.1): a
session created — by login or step-up rotation, on Porch's clock — after the request, or an `auth_time` no older than
`max_age` seconds before the request (whole seconds; upstream `auth_time` may be skewed). zitadel turns `prompt=login`
into `max_age=0`; an earlier "now − auth_time ≤ max_age" check looped forever for real clients (found by the OpenID
conformance suite, `oidcc-prompt-login`). `prompt=login` additionally records which session was sent to
re-authenticate; the request continues only when that session came back *rotated* (a step-up always rotates) with an
`auth_time` inside the step-up window. Federated sessions re-authenticate upstream with `prompt=login&max_age=0`
(Google: an interactive `prompt=select_account` sign-in, ADR-0047);
backup sessions repeat the two-step backup login. `prompt=none` never shows UI: no session, a due upstream recheck or a
required re-authentication yield `login_required`.

## ADR-0032 — No consent screen for administrator-registered applications

**Decision.** Applications are registered by installation operators for their own tenants (first-party in this
deployment model), so Porch does not show a per-user consent screen. What an app receives is controlled by the app's
disclosure settings and the client's allowed scopes. Setup and recovery-link sessions cannot sign in to applications.
**Consequences.** Revisit if third-party/self-service app registration is ever added (Backlog).

## ADR-0033 — Access-token revocation is best effort

**Decision.** Access tokens are self-contained JWTs (≤ 10 min by default). Revocation (RFC 7009, code replay, logout)
adds the `jti` to a denylist honoured by Porch's own userinfo and introspection endpoints. Resource servers that verify
JWTs offline do not see the denylist; they bound exposure by the token lifetime or use introspection. Refresh-token
revocation is immediate.

## ADR-0034 — Application access modes and cross-tenant shares

**Decision.** Every application has an `access_mode`: `all_members` (default; every active member of the owning tenant,
and of tenants it is explicitly shared with, receives an implicit `app:access` grant shown as `implicit:all_members` /
`share` in the explain trace) or `assigned` (only explicit `app:access` grants: a role on the app, on the `app` resource
type or at tenant scope). A share (`app_shares`) is the only way a member of another tenant passes the tenant gate for an
app; it never confers anything else. Tokens and forward-auth headers name the tenant through which access was granted
(`porch.tenant`), so a shared Jellyfin knows which family a viewer belongs to. Deny policies of the owning tenant still
apply to shared access.

## ADR-0035 — The authorization engine ships in M4, its admin tooling in M5

**Context.** Application access (M4) needs `app:access` decisions with conditions and deny policies; building a
temporary rule system would be thrown away.
**Decision.** The engine (ADR-0011/0012) is complete in M4 and used by OIDC authorize, every token issuance, forward-auth,
the launcher and `POST /tenants/{t}/authz/check`. M5 adds the admin UI, effective-permission views, the policy simulator
UI and delegation to tenant admins (with escalation checks: a tenant admin may grant only what they hold). Until then
model changes are made by installation operators through services and tests (ADR-0026).

## ADR-0036 — Forward-auth details

**Decision.**
- `/outpost/auth` answers only peers in `forward_auth.trusted_peers` (default: `proxy.trusted_proxies`) or loopback.
- Unauthenticated GET/HEAD → 302 to `<porch>/outpost/start?rd=<original>`; other methods and JSON requests → 401.
- `rd` must be an absolute https (http only in development) URL on a host registered to an enabled forward-auth app.
- The one-time code (60 s) is bound to the host and is burned by any redemption attempt, even on the wrong host.
  Since the M7 review it is also bound to the browser: `/.porch/callback` sets a host-only nonce cookie and sends the
  browser to `/outpost/confirm`, which accepts only the Porch session the code was issued to and issues a second code
  bound to the nonce, redeemed at `/.porch/finish` (no forward-auth login CSRF).
- The host-only `__Host-porch_fa` cookie lives at most `forward_auth.session_ttl` (12 h) and never longer than the Porch
  session; every request re-checks the Porch session (revocation, epochs, hourly upstream recheck) and `app:access`.
- Identity headers default to `X-Porch-User` (sub), `X-Porch-Email`, `X-Porch-Name`, `X-Porch-Groups`, `X-Porch-Tenant`;
  values are single-line. Proxies must strip client-supplied `X-Porch-*`/`Remote-*`; Porch overwrites the headers it
  sends, but headers it does not send are the proxy's responsibility.
- Backends reachable without the proxy bypass all of this (documented).

## ADR-0037 — Service accounts

**Context.** Backups jobs, scripts and APIs need a tenant identity that is not a person, can hold roles and can obtain
access tokens without a browser.
**Decision.** A service account is a tenant-scoped row (`service_accounts`, ID prefix `sva_`) with a Porch-generated
secret (`porch_sa_…`, shown once, stored as an HMAC under the keyring token key with its own MAC domain, so it can never
be confused with an application client secret). It authenticates at `/oauth2/token` with the client credentials grant
using its ID as `client_id` (`client_secret_basic` or `_post`); access tokens are RFC 9068 JWTs with `sub` = `client_id` =
the service account ID, audiences from its registered list (RFC 8707 `resource` must be one of them), lifetime 60–3600 s.
No ID tokens, refresh tokens, authorization-code or user-info access. Service accounts are authz subjects
(`subject_type: service_account`): they pass the tenant gate of their own tenant only, never receive the implicit
`all_members` grant, and fail every check while disabled. Deleting one removes its assignments in the same transaction
and bumps the authz epoch. Rotation needs a recent sign-in and invalidates the old secret immediately.
**Consequences.** Machine access is auditable (`actor_type: service_account`, `last_used_at`) and revocable without
touching applications. Automation tokens for the management API (M6) are a separate mechanism.

## ADR-0038 — Delegated tenant administration and escalation checks

**Context.** Families and friend groups want one of their own to manage members, apps and roles without being an
installation operator (ADR-0026 was a stop-gap).
**Decision.**
- Every tenant-scoped management endpoint names one permission (`member:manage`, `app:manage`, `invite:manage`,
  `role:manage`, `group:manage`, `resource:manage`, `policy:manage`, `service_account:manage`, `audit:read`,
  `authz:simulate`, `tenant:manage`). Installation owners/admins act as operators (`tenancy.ViaOperator`); anyone else
  must be an active member for whom the engine allows that permission on the tenant (`tenancy.ViaDelegated`, built only
  by `ResolveDelegated` after the check). Callers without access get 404, indistinguishable from a missing tenant.
- **Escalation rule.** A delegated administrator may only grant, define, confer or remove what they hold
  *unconditionally at tenant scope* (`Engine.Missing`; conditional, expiring-later or resource-scoped grants do not
  count): role definitions (permissions plus everything bundled roles grant), assignments (create and delete), group
  membership and nesting (everything the group and its ancestors are assigned), deleting roles, groups and service
  accounts that hold permissions, deny policies (their actions; `*` means `*:*`) and changes to condition policies (every
  role whose assignments reference it). Violations return 403 `privilege_escalation` listing the missing permissions.
  The built-in `admin` role holds `*:*`, so only tenant admins and operators can hand it out.
- Installation-wide matters stay with operators: tenant status and deletion, cross-tenant shares, domain rules (domains
  are unique installation-wide), identity providers, users, sessions of other users, signing keys.
- Policy writes and secret rotations still need a recent sign-in (ADR-0010).
**Consequences.** `Missing` and the engine agree by construction (property test `TestEscalationCheckProperty`). A tenant
admin can remove other members' non-admin grants they hold themselves; they can lock themselves out, which an operator
can repair. Delegation is enforced only in the API; the UI hides what `/me/admin` says is unavailable.

## ADR-0039 — Operations views: audit explorer, sessions, system health

**Decision.**
- `GET /audit` (owner, admin, auditor) and `GET /tenants/{t}/audit` (`audit:read`, that tenant's rows only) filter by
  actor, target, action prefix (`[a-z_.]`), outcome and time, newest first with an opaque `seq` cursor. The API returns
  plain details only; sealed details (`details_enc`) are never decrypted by the API and are flagged `sealed_details`.
  Each row carries a chain-hash prefix for cross-checking exports.
- `GET /sessions`, `DELETE /sessions/{id}` and `POST /users/{u}/revoke-sessions` (step-up) are installation-operator
  only: sessions are installation-wide, so a tenant admin ending a session would affect the user's other tenants.
  Tenant admins remove access by suspending or removing the membership instead. Revocations are audited.
- `GET /installation/health` (owner, admin, auditor) reports readiness, storage state and sizes, keyring versions,
  outbox backlog, open alerts, counts and named checks (`ok` / `warning` / `critical`); backups report "not configured"
  until M6.

## ADR-0040 — Admin UI accessibility and CSP adjustments to Mantine defaults

**Context.** axe (WCAG 2.1 AA) runs on every admin page and dialog in the e2e suite and the CSP forbids un-nonced
`<style>` elements. Several Mantine 8 defaults fail.
**Decision.**
- The light-scheme text colour of the `light` variant (badges, alerts, light buttons) is set per palette colour to a
  value with at least 4.6:1 contrast on the variant's tint over white and over striped table rows (computed; shade 6,
  Mantine's default, fails for most colours and even shade 9 fails for green, lime, orange, red, teal, yellow).
  `--mantine-color-error` uses red-9 (5.5:1 on white).
- Modal, Drawer and Notification close buttons get accessible names through theme defaults.
- Modal and Drawer scroll locking is disabled: `react-remove-scroll` injects a `<style>` element without the CSP nonce.
  Background scrolling while a dialog is open is the accepted cost; relaxing `style-src-elem` is not.
**Consequences.** New colours or components must keep axe clean in the e2e suite; the suite fails otherwise.

## ADR-0041 — Automation tokens and Idempotency-Key (security-relevant change)

**Context.** Terraform and scripts need non-interactive access to the management API; retries must not create
duplicates or leak secrets twice.
**Decision.**
- `porch_at_<43 base64url chars>` bearer tokens (32 random bytes) stored as HMACs under the keyring token key (own MAC
  domain), shown once, with a mandatory expiry of 1–366 days (except owners' installation tokens, ADR-0046), `last_used_at`/`last_used_ip`, revocation, audit
  (`actor_type: automation`, `auth_method: automation`, provenance `automation:<token id>`).
- A token acts for its creator and never for more than the creator holds *now*: installation tokens carry `admin` or
  `auditor` and work only while the creator still holds an installation role that covers it (owner/admin for admin);
  tenant tokens carry one tenant and a permission list, issued only with permissions the creator holds (ADR-0038
  escalation check) and every request needs both the token's permission and the creator's current right (operators'
  tenant tokens use the operator scope, still limited to their tenant and permissions). A disabled creator disables
  all their tokens.
- **Security-relevant change:** bearer requests skip the Origin/CSRF checks (no ambient credential) and **skip step-up**
  (ADR-0010) — a token is itself issued under step-up by an owner or a tenant administrator and is short-lived by
  policy. To limit the blast radius, tokens are refused for: issuing tokens, granting or revoking installation roles,
  rotating signing keys, unlocking backup logins, logout and every state-changing `/me/*` operation (credentials,
  linking, personal sessions). *(Amended by ADR-0048: tokens may issue narrower tokens.)*
- `Idempotency-Key` (1–255 printable ASCII) on any authenticated POST: the key is scoped by a MAC of the presented
  credential and bound to a SHA-256 of method, path and body; a repeat returns the stored 2xx response
  (`Idempotent-Replayed: true`), a different request with the same key gets `422 idempotency_key_reused`, a concurrent
  one `409 idempotency_in_progress`. Responses containing `client_secret`, `token` or `secret` are stored without the
  body and replay as `409 idempotent_secret_withheld` with a `Location` header. Failed requests are not stored. Keys
  live 24 h.
**Consequences.** A leaked token is usable until it expires or is revoked; secret scanners can match the prefix.

## ADR-0042 — Encrypted backups and restore

**Decision.**
- A backup is a `VACUUM INTO` snapshot plus (unless `backup.exclude_kek`) the encoded KEK, each S2-compressed and
  encrypted with age to the configured offline X25519 recipients, uploaded to S3-compatible storage
  (`<prefix>backups/<bkp_id>/{db.age,kek.age,manifest.json}`) through the SSRF-guarded transport. Porch holds no
  identity: it can write backups but not read them.
- `manifest.json` (written last; marks a complete backup) lists every object with plaintext and ciphertext SHA-256,
  schema version, installation and KEK IDs. It is **signed with Ed25519** (key derived from the keyring `backup-meta`
  purpose key). Recipients are public, so anyone with write access to the bucket could otherwise plant a complete,
  well-encrypted forged installation; `porch restore` refuses unless one of the supplied verification keys
  (`porch-backup-ed25519:…`, shown in the admin UI, the server log and `porch backup verify-key`) verifies the manifest.
  `--insecure-skip-verify` exists for lost keys and is recorded in the restore alert.
- Schedule: first backup at start, then every `backup.interval` (default 6 h, the RPO) after the last success; failures
  retry after 15 minutes; manual runs via API/UI (`POST /installation/backups`) or `porch backup run` (server stopped).
  Retention keeps the newest `backup.retention` complete backups (manifest deleted first so a partly deleted backup is
  never mistaken for a complete one); deletions failing under object lock are logged, the backup still counts.
- Restore (`porch restore`) only writes into an empty data directory and a non-existent KEK path (0400), then leaves a
  marker; the next start bumps the installation security epoch (every session and refresh token from the backup is
  invalid), rotates and immediately retires the ES256/RS256 signing keys, raises a critical `installation_restored`
  alert and audits `installation.restored`. `--invalidate-backup-logins` deletes all backup-login credentials (reusable
  recovery answers restored from an old state are the main residual risk).
- Health: the `backups` check is critical when the last run failed or the last success is older than two intervals.
**Consequences.** RPO = interval; the restore drill (`scripts/backup-drill.sh`, MinIO with versioning + object lock)
takes seconds for a small installation; RTO target < 30 min is dominated by fetching the identity from offline storage.

## ADR-0043 — Event relay to pulse

**Decision.** Implements ADR-0019 with the go-pulse SDK (pinned pseudo-version of the public `main`): a single relay
goroutine polls due outbox rows every 2 s (draining backlogs without waiting), publishes each with
`Nats-Msg-Id` = the outbox ID, `ce-type` `porch.<area>.<entity>_<action>.v1`, `ce-time` = enqueue time, subject
`evt.porch.<area>.<entity>.<action>`, payload = the non-secret JSON stored at enqueue. On failure the row backs off
(2^(n-1) s ± 50 %, cap 5 min) and the round stops (pulse is probably down); after 50 attempts or 24 h it is
dead-lettered (`porch_outbox_events{state="dead"}`, alert `PorchOutboxDeadLetters`). Connection failures retry every 30 s;
requests never wait for pulse. Published rows are purged after 7 days.
**Consequences.** Delivery is at-least-once: JetStream de-duplicates retries within its window (2 min in pulse) and
consumers must de-duplicate on the event ID beyond it. Verified against an embedded NATS JetStream through the SDK and
against a running pulsed (`test/pulse/verify.sh`).

## ADR-0044 — Changes from the M7 security review (security-relevant change)

**Decision.** See `docs/SECURITY_REVIEW-2026-10-24.md` for every finding. Behaviour changes worth knowing:
- Forward-auth reads the original request only from `X-Forwarded-Proto/Host/Uri`; `X-Original-URL` is ignored.
- The escalation rule (ADR-0038) now also: excludes expiring grants, evaluates deny policies for the caller, covers
  policies keyed on group slugs, role stripping, resource deletion, member suspension/removal and service-account
  rotate/update; automation tokens are never exempt, even when created by an operator.
- Leaving a tenant deletes the user's assignments there (database trigger on every membership delete).
- Audiences are owned by one tenant; client-credentials scopes must be registered; disabled tenants' clients get no
  tokens; creating a service account or confidential client needs a recent sign-in.
- RP-initiated logout changes state only when the `id_token_hint` names the user of the current Porch session
  (otherwise it only redirects: an RP without hints no longer ends the Porch session).
- Restore revokes every automation token and retires every non-active signing key.
- Follow-up fixes: automation tokens of users with external identities work only while the identity provider confirmed
  the user within `automation.upstream_max_age` (default 30 days); forward-auth sign-in is bound to the browser
  (ADR-0036); a replayed authorization code revokes tokens even if the first exchange is still in flight; the login
  callback is throttled; a provider that omits `auth_time` never satisfies step-up or linking; delegated application
  managers register forward-auth hosts only inside the tenant's domain-rule domains and need `app:access` to open an
  application to all members.

## ADR-0045 — Appearance: login backgrounds and application icons

**Context.** The user-facing pages (sign-in, launcher, account) should look like a finished product: a landscape
background on the sign-in page and logos for applications, as Authentik offers. Images come from the internet, which
adds outbound requests and content that browsers render.
**Decision.**
- Porch fetches every image itself, through the outbound guard (public addresses only, every redirect hop checked),
  with size limits (icons 2 MiB, backgrounds 25 MiB) and a 64-megapixel header check before decoding. It decodes and
  re-encodes the image (raster icons: PNG ≤ 256×256; backgrounds: landscape JPEG ≤ 2560×1600) and stores only the
  re-encoded bytes in the `media` table, keyed by their SHA-256. SVG icons stay SVG (they scale cleanly) but are parsed
  and rewritten from an allowlist: shapes, paint servers, clipping, masks, text, styles and filters are kept; scripts,
  `foreignObject`, images, links, animation, event-handler attributes, `href`s outside the document and
  `javascript:`/`data:`/external `url()` values are removed, and documents with a DOCTYPE are refused (no entity
  expansion). `GET /media/{id}` serves everything from Porch's origin with `nosniff`,
  `Content-Security-Policy: default-src 'none'; sandbox` (scripts cannot run even when an SVG is opened directly) and
  immutable caching; the UI shows icons only through `<img>`. Browsers never contact a third party (no visitor IPs
  leak to image hosts) and the page CSP stays `img-src 'self'`.
- Backgrounds (installation setting, `PUT /installation/appearance`, owner/admin) come from a list of providers that
  fill one pool in turn; an empty list (the default) means no backgrounds and no outbound requests. Providers:
  `wikimedia` (Wikimedia Commons: a category, default "Featured pictures of landscapes", or named files; openly
  licensed, with author and licence shown as a credit), `picsum` (Lorem Picsum photos from Unsplash: random, or by ID;
  no categories) and `url` (the operator's own https image URLs). A provider that fails leaves its share to the others.
  Porch keeps 1–24 images, renews them daily, weekly or never, and shows a random one per visit or one per day.
  Commons metadata is stripped to plain text; panoramas wider than 2.6:1 and portrait images are skipped.
- Application icons (`app:manage`): upload (≤ 512 KiB), an https URL, a brand logo from theSVG (glincker/thesvg, MIT
  code; each logo keeps its brand's licence and trademark; from thesvg.org, falling back to the GitHub repository), or
  a name from the dashboard-icons set (homarr-labs, Apache-2.0; SVG, else PNG; via jsDelivr). Applications also get a launcher `group`.
- `GET /api/v1/appearance` is public (title and current background with its credit).
**Consequences.** Tenant application managers can make Porch fetch public URLs (bounded by the guard, size and type
limits). Icons and backgrounds are part of database backups. Picsum and Commons availability affect only refreshes;
the stored pool keeps working offline.

## ADR-0046 — Installation tokens without expiry for owners (security-relevant change)

**Context.** ADR-0041 requires every automation token to expire within 366 days, and review L3 (ADR-0044) stops
tokens of users who sign in through an identity provider when the provider has not confirmed them for
`automation.upstream_max_age`. For the installation owner's own Terraform or break-glass automation this is a single
point of failure: an expired token, or a Google outage or account problem, locks automation out of Porch exactly when
it is needed to repair the identity provider configuration.
**Decision.** An installation owner may issue an *installation* token with `never_expires: true` (UI: "Never
expires"). Such a token:
- has no expiry (`expires_at` is omitted in the API; the row stores a far-future value so every expiry comparison and
  cleanup holds unchanged) and is exempt from the upstream-confirmation rule;
- can only be issued interactively: installation tokens are owner-only, need a recent sign-in, and tokens never hold
  the owner role, so no token can mint another *(amended by ADR-0048: a never-expiring token whose creator is an owner
  may issue another one)*;
- still acts for its creator: it stops when the creator is disabled or loses the owner/admin role, and revocation ends
  it immediately;
- is audited (`automation_token.created` with `never_expires: true`) and shown with a "never" badge in the token list.
Tenant tokens and non-owners keep the 1–366 day limit and the upstream rule.
**Consequences.** **Security-relevant relaxation:** a leaked owner token stays valid until someone revokes it, and it
keeps working for a creator removed from the upstream directory (but not for one disabled in Porch). Operators should
store it like a root password, watch its last-used time and address, and revoke it when it is no longer needed.

## ADR-0047 — Step-up and linking with providers that cannot re-authenticate (security-relevant change)

**Context.** ADR-0010 and ADR-0005 satisfied step-up and identity linking with a fresh upstream sign-in: `prompt=login`,
`max_age=0` and an `auth_time` inside the step-up window. Google supports neither: "Google does not support Google
Account reauth requests", `prompt` accepts only `none`, `consent` and `select_account`, and `auth_time` is sent only to
verified apps that enabled session age claims and asked for it. The fake provider used in tests always sent a fresh
`auth_time`, so every Google step-up and every Google link failed with real Google ("the identity provider did not
perform a fresh sign-in"), and an OIDC client's `prompt=login` or `max_age` could not be satisfied for Google users.
**Decision.** Providers of kind `google` are treated as unable to re-authenticate on request. For them, step-up,
linking and downstream re-authentication send `prompt=select_account` and accept a completed interactive sign-in: the
authorization code flow with PKCE, nonce and a state bound to this browser's login cookie, returning the identity
already linked to the session (step-up) or not linked to anyone (linking). Porch records the completion time as the
authentication time; Google's `auth_time`, when present, is the age of the Google session and is not used. Linking
still needs a recent Porch sign-in first. Providers of kind `oidc` keep the strict rule: `prompt=login`, `max_age=0`
and a recent `auth_time`, else `stale_auth`. The test provider omits `auth_time` like Google by default.
**Consequences.** **Security-relevant relaxation:** for Google users, step-up proves that the person at this browser
can complete a Google sign-in as the session's user now. That defeats a stolen Porch session cookie used elsewhere
(the thief has no Google session for the victim) but not someone at the victim's unlocked device with Google still
signed in; there, Google's own session policy (re-authentication settings, device lock) is the control. Relying
parties that send `prompt=login` or `max_age` get the same guarantee for Google users. Users who need a stronger
step-up use the backup credential.

## ADR-0048 — Read-only access and tokens issued by tokens (security-relevant change)

**Context.** A read-only integration (the Deed connector reading applications and service accounts) needed a write
credential: Porch had no read-only tenant permission for applications or service accounts, and an installation
`auditor` token reads health and the audit log but nothing inside a tenant. Terraform, which authenticates with an
automation token, could not create the token for such an integration, because ADR-0041 made token issuance
interactive-only.
**Decision.**
- **Read permissions.** `app:read`, `tenant:read`, `member:read`, `group:read`, `role:read`, `policy:read`,
  `resource:read`, `invite:read` and `service_account:read` join the system catalogue. Each allows the management API's
  reads of its area and nothing else; the matching `:manage` permission keeps allowing them. Shares and domain rules
  stay readable only by installation operators and inspectors. `X:manage` does not imply `X:read` in the
  authorization engine (custom permissions keep their exact meaning); the API accepts either for a read.
- **Inspector role.** A new installation role `inspector`, for people and for installation tokens, reads the
  configuration inside every tenant: the tenant, applications and their shares, service accounts, members, groups,
  roles, the permission catalogue, assignments, effective permissions, resources, policies, invitations and domain
  rules, plus the tenant list and identity providers. It reads through its own tenant scope (`via: inspector`), which no
  write operation accepts, and gets no audit log, health, users, sessions or tokens (the `auditor` role keeps those,
  unchanged). Responses never contain secrets, only their last characters. Only owners grant the role, interactively.
  An inspector token works while its creator holds `owner`, `admin` or `inspector`.
- **Tokens issued by tokens.** Token issuance is no longer interactive-only:
  - an installation token may issue tokens only while its creator is an installation **owner**, and only tokens no
    broader than itself: an `admin` token issues installation tokens of any role and tenant tokens; a token issued
    with `never_expires` needs an issuer that never expires;
  - a tenant token issues tenant tokens of its own tenant with permissions it holds (and its creator holds, as for
    people);
  - a **read-only** token (auditor, inspector, or a tenant token whose permissions all end in `:read`) issues nothing;
  - an issued token never outlives its issuer, records it (`issued_by`), acts for the same creator, and is revoked
    with it: revoking a token revokes every token it issued, transitively (at most 8 deep). A token can read and revoke
    the tokens it issued, so Terraform can manage them.
  People still need a recent sign-in to issue tokens; `issued_by` is in the audit details of `automation_token.created`.
**Consequences.** **Security-relevant relaxation:** a stolen admin token whose creator is an owner can mint more
tokens, including another never-expiring one when it never expires itself. Containment: every minted token is no
broader than the stolen one, stops when the creator loses the owner role or is disabled, and is revoked together with
the stolen token, so revoking the token found in a leak ends the whole tree. Read-only tokens cannot mint anything.
The inspector role widens what a read-only installation credential sees (every tenant's configuration, including
members' names and email addresses); grant it like an administrator role.
